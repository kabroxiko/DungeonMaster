# Dungeon Master Prompt Catalog

This document describes prompt templates embedded in `gmai-server` from this directory. Edit files here; paths are relative to `go/internal/prompts/promptfiles/`.

## Directory layout

| Folder | Role |
|--------|------|
| `core/` | Always-on DM persona and global style (`system`, `style`). |
| `rules/` | Guards, language directives, memory wrapper, intent router, scene grounding. |
| `skills/` | Mode-specific skills (combat, investigation, decision, adventure seed, character gen). |
| `templates/dm/` | Mustache injections, response envelope, party/PC context, combat handoff. |
| `templates/campaign/` | Campaign core generator (merged file + stage templates). |

## Skill file format

Every prompt file is a Markdown skill file (`.md`) that opens with YAML frontmatter:

```markdown
---
name: adventure-seed
description: Opening-scene seed covering structure, length, story hook and first-opening naming rules.
---

...prompt body...
```

- `name` is a unique kebab-case skill id, `description` is one sentence saying when the block applies.
- `prompts.Load` strips the frontmatter before caching, so only the body ever reaches a model prompt. Tooling and editors see the metadata; the model does not.
- Never add a second frontmatter block inside a body. `templates/campaign/generator.md` splits on a single `---` line, and stripping happens first, so that separator stays unambiguous.

## Loading

- `promptmgr.LoadPrompt(name)` expects a path relative to this tree (e.g. `rules/language_spanish.md`, `templates/dm/inject_initial.md`). `.txt` paths no longer resolve — every prompt is a `.md` skill file.
- `prompts.Load` (in `go/internal/prompts/embed.go`) drops the frontmatter and trims the body.
- `loadCampaignGeneratorParts()` reads `templates/campaign/generator.md`, splits on a single `---` line: **build context** (system, world-only JSON rules) and **user template** (Mustache with `{{sessionSummary}}`, `{{languageInstruction}}`). `/generate-campaign` and `/generate-campaign-core` use both slices (build + full user text as system priming, then rendered user text as the user message), matching the old two-file behavior.

## Flow notes

- System messages are consolidated via `consolidateSystemMessages(...)` before sending to the model to preserve guard precedence.
- Campaign core is generated by `/generate-campaign-core` using `templates/campaign/generator.md`. The API persists `campaignSpec`.
- Background stages use `generateCampaignStage` with `templates/campaign/stage_*.md`.
- For initial adventures, `renderInitialCampaignInject` (`go/internal/gamesession/dm.go`) renders `templates/dm/inject_initial.md` from the stored `campaignSpec` and prepends it to the `/generate` system stack, so the opening is written from the campaign's concept, conflicts, factions, NPCs and key locations instead of being invented. The stored `openingSceneFrame.directive` is injected as a mandatory instruction, and any place name it took from the old key locations is rewritten to the map name that replaced them (`reconcileDirectiveNames`). Key location names are reconciled against the players' map at render time (`campaignspec.AlignKeyLocationsToWorld`), which also repairs campaigns generated before place-name alignment existed, and the map's place names are listed with their kinds as the only settlements the opening may name.
- **Vellaris worlds:** every game carries `campaignSpec.vellarisWorld`, and `renderVellarisWorldInject` prepends `rules/vellaris_world.md` + the rendered `templates/dm/world_vellaris.md` to the `/generate` system stack. There is no second, invented topology: the map service is the only source of geography, so no template asks the model for a region graph and no code path injects one. The same block also feeds `templates/campaign/stage_keyLocations.md` through `{{#hasVellarisRegions}}` / `{{vellarisRegions}}` **and `{{#hasVellarisPlaces}}` / `{{vellarisPlaces}}`**, so key locations are chosen from the map's own named places and tagged with regions that already exist. `campaignspec.AlignKeyLocationsToWorld` then enforces that guarantee server-side: a name the map knows is kept with the map's spelling, an invented or repeated name takes the next unused map name, and a location with no map name left is dropped — the model contributes `type` and `significance`, not geography. Key locations are aligned against **settlements only** (`SettlementNames`), never regions or lakes. **Every** campaign stage (factions, majorNPCs, keyLocations, opening frame) also gets `rules/vellaris_world.md` + `templates/campaign/world_context.md` in its system stack (`campaignWorldSystemBlock`), and the campaign core's build context lists the map's named places (`{{vellarisPlaces}}`, top 24) with a rule that any settlement named must come from them and at least two must be used.
- **Kinds:** Vellaris names are what they are, and the prompts say so. `campaignspec.PlaceKind` maps a map-text type to the word used everywhere (`City` → `settlement`, `Landmark` → `landmark`, `Region` → `region`, `Lake`/`River` → `lake`/`river`, `Mountain_range`/`Other_mountains` → `mountains`, `Title` → `map title`). Normalized regions carry `type: Region` and `kind: region`; normalized places carry `kind`, and **region labels and the map title are not listed as places** (regions already have ids). `rules/vellaris_world.md` requires the DM to respect the kind — a region is a territory (“in the region of X”), only settlements have streets and markets. Stored campaign documents are decoded from MongoDB, where arrays are `primitive.A`; `campaignspec.neighborSliceAny` and `llm.SliceValues` accept any slice type so a stored world is never mistaken for an empty one.
- **Surroundings:** every named place also says what the ground around it is like, read from the map's Voronoi graph (`surroundings.terrain`, `nearbyTerrain`, `coastal`, `lake`, `river`, `riverNearby`, `mountains`, `island`), and every region reports the terrain most of its land is (`regions[].terrain`). A place also reports the region it belongs to (`regionId`, `regionName`, `regionSuffix`), and `AlignKeyLocationsToWorld` overrides a key location's `regionId` with that region, so a settlement cannot be filed under a territory it is not in. `campaignspec.surroundingsText` renders the place part as the phrase after each place name in `world_vellaris.md`, `campaign/world_context.md`, `campaign/generator.md`, `stage_keyLocations.md`, `character/world_context.md` and `inject_initial.md`; region terrain renders beside the region name in the same blocks. `rules/vellaris_world.md` and `rules/character_world.md` forbid contradicting either: a desert place or region has no river, stream or woods and an inland place has no harbour, so narration uses wells, cisterns and caravan roads instead. Nothing is added when the world reports nothing, so an older stored world simply prints names and kinds as before — its terrain appears once its world is regenerated.
- **Campaign generation runs on the map.** `prepareCampaignWorld` (`go/internal/gamesession/campaign_world.go`) runs before the creative seed and before any campaign text: a game that already has `campaignSpec.vellarisWorld` reuses it, otherwise the map service is asked once (`POST /api/world`) with settings from the request's `worldSettings` or from `DM_VELLARIS_SETTINGS_FILE`, and the answer is stored before generation continues. The settings are stamped with the game's language (`resolveCampaignLanguage` → `withCampaignLanguage`), so Vellaris generates place and region names in the language the table plays in; `rules/vellaris_world.md` and `rules/language_spanish.md` both state that world names keep that spelling rather than being translated to English. The rendered map image (`POST /api/world/map`) is downloaded in parallel with the campaign stages, and stored and announced on the game state **as soon as it arrives**, not when the last stage finishes: the picture describes the world, which is already stored, so a client can fetch it (and warm its browser cache) during the wait for the campaign text instead of on the click that opens the map. `startCampaignWorldMapSave` owns that, and each caller awaits its warning before writing `campaignSpec` back, since that write replaces the spec the marker lives in. That world block is rendered by `templates/campaign/world_context.md` and reaches both the generator's system stack (`BuildCampaignCoreSystemMsgs`) and its build context (`{{#hasVellarisWorld}}` / `{{vellarisRegions}}` in `generator.md`).
- **The map can be marked during play.** A DM reply may carry an optional `newPlaces` array (`[{name, x, y}]`, at most one site, declared in `templates/dm/player_response_envelope.md`, allowed by `rules/vellaris_world.md`, and explained where the world block is rendered in `templates/dm/world_vellaris.md`). `gamesession.ParseNewPlaces` reads it, and `StartMapPlaceUpdate` runs `ApplyMapPlaces` (`go/internal/gamesession/map_places.go`) in the background after the turn is stored, so a multi-second render never delays narration. `ApplyMapPlaces` calls Vellaris (`POST /api/maps/{id}/places`, or `POST /api/world/places` for a stateless service), then stores the returned world, the canonical settings (stateless only) and the re-rendered image together, sets a fresh `campaignSpec.mapImage.updatedAt` (clients key the image URL on it) and broadcasts a state update. The added landmark arrives as a `Landmark` map-text place, so it reaches the next turn's world block through the normal normalization path and `PlaceKind` reports it as `landmark`, never as a settlement. Duplicate names are skipped by the service and coordinates over open water are refused, so a failed mark costs a log line, not the turn.
- **The party pin rides on the same map.** A reply may carry an optional `partyPosition` (`{place}` or `{x, y, note}`, declared in `templates/dm/player_response_envelope.md`, allowed by `rules/vellaris_world.md`). `gamesession.ParsePartyPosition` reads it and `ApplyPartyPosition` (`go/internal/gamesession/party_position.go`) stores `campaignSpec.partyMapPosition` as a **fraction of the rendered image**, so nothing is re-rendered and no new image is downloaded: `campaignSpec.mapGeometry` holds the projection from world coordinates to image fractions (resolution, generated size and the border padding when the border is drawn outside the map), and is computed once from the map's settings and then kept. `mapGeometry` is DM-only arithmetic; `partyMapPosition` stays in the client view as a map marker. `renderPartyPositionInject` renders `templates/dm/party_position.md` from the stored position, so every turn — the opening included — plays from that pin. **The pin exists before the first turn:** `stage_openingSceneFrame.md` returns `openingSceneFrame.startPlace`, one settlement copied from the map, and `storeOpeningPartyPosition` resolves it (falling back to the campaign's key locations, which are settlement names) into `partyMapPosition` at campaign generation. A place name the map does not have — a region, or an invented one — never becomes a pin, so the party always opens on an exact spot. The client draws the dot inside the same layer as the picture it already shows and reuses the stored fraction, which survives any downscaling of the picture.
- `campaignSpec.vellarisWorld` and `campaignSpec.vellarisSettings` are DM-only: `RedactCampaignSpecForClient` removes them (they carry coordinates players must not see) and `HasSubstantiveCampaignSpec` ignores them, so storing a world early does not make an unfinished game look ready. Clients learn about the rendered map through `campaignSpec.mapImage`, which is a **map marker, not campaign content**: `campaignspec.mapMarkerKeys` keeps `mapImage` / `mapImageError` out of the readiness check (mirrored in `campaignSpecReady.js`), because character generation stores the map before any campaign exists and a game holding only a map must still be startable.
- **Characters are written on the same map.** `/generate-character` calls `campaignWorldForCharacter` (`character_world.go`) before it builds its prompt: a game that has no `campaignSpec.vellarisWorld` yet creates one, exactly as the campaign path does, and a game that has one reuses it. World creation is serialised per game id (`lockCampaignWorld`), so two players pressing generate at the same moment get **one** world — the second waits on the lock and then reads what the first stored — and no table ever ends up with a different map per player. The block that reaches the prompt is `rules/character_world.md` + `templates/character/world_context.md` (`characterWorldSystemBlock`, 12 places): the PC's homeland must be one of the listed regions or places and every place named in `brief_backstory` must be copied from that list.
- `campaignSpec.vellarisWorld` mirrors what the map service returns, so importing a world is a copy rather than a rewrite: `{seed, worldSize, imageWidth, imageHeight, mapImageUrl, regions[{id,name,terrain,centerX,centerY,centerCount}], places[{name,type,x,y,surroundings{terrain,nearbyTerrain,coastal,lake,river,riverNearby,mountains,island}}], routes[{from,to,distance,days,crossesWater,regionsCrossed,terrain[{terrain,share}]}]}`. `campaignspec.NormalizeVellarisWorld` formats every value for the prompt and caps it, so the templates never print float noise. `surroundings` is the map's own answer for the ground around a place (its terrain, the bordering terrain, whether the coast, a lake, a river touching it or only a river near it, mountains or an island are at hand, and whether a place on an island is on its shore or inland); `surroundingsText`/`surroundingsSuffix` are the phrase the templates print, and a world that reported nothing gets no phrase rather than an invented terrain.
- `skills/adventure_seed.md` defines the adventure seed (structure, **story hook vs. paperwork** so openings are not “papers please” alone, **First opening** appendix: no PC proper name in prose before the first user message).
- `skills/character.md` contains system-level character rules and a user-level template section (marked in the file). The API renders the user section as the user message.

## Editing

- Use Mustache-compatible variables (e.g. `{{campaignConcept}}`, `{{#factions}}...{{/factions}}`, `{{languageInstruction}}`).
- Keep the `name` unique and the `description` accurate: they are the only metadata a reader or agent tool has for the file.
- If you add, rename or delete a file, update every `LoadPrompt` / Mustache usage in `go/internal/gamesession/` and `go/internal/promptmgr/` and this doc.

## Troubleshooting

- If a stage fails, `GameState.rawModelRequest` and `GameState.rawModelOutput` are populated for debugging.
- The server logs outgoing messages as `OUTGOING` / `DEBUG` entries — check terminal logs.
